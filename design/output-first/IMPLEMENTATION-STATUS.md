# حالة تنفيذ الخطة — 2026-09-21

**الحالة: نسخة تنفيذية أولية قابلة للتجربة، وليست اكتمال الخطة أو اعتماد المنتج على مشاريع غير معروفة.**

تم تعديل المحرك وإضافة واجهة تشغيل واختبارات فعلية. لا تُعدّ مواصفات التصميم أو الاختبارات الآلية بديلًا عن مراجعة جودة الاستنتاجات. لا يوجد نموذج حي أو تقييم بشري مستقل في نتائج هذه الجولة.

## ما يعمل الآن

```bash
# من جذر الريبو؛ مجلد التقرير خارج المشروع المستهدف
.venv/bin/python -m eaos review-project /absolute/project \
  --out /workspace/project-review --goal evolution --lang ar

# نفس المسار مع مزود اختاره المستخدم وتهيئته المعتادة
.venv/bin/python -m eaos review-project /absolute/project \
  --out /workspace/project-review-semantic --provider /absolute/provider.json
```

المخرجات: `PRODUCT-REPORT.md`، موجز القرار، خريطة النظام، التدفقات، العقود، بطاقات PLAN وموجاتها، `BLOCKERS.md`، سجل JSON و`index.html`. التشغيل دون مزود يحمل صراحة وصف facts-only. اختيار الهدف يوجه العرض ومدخل النموذج؛ لا يدعي تنفيذ محلل مختلف لكل هدف.

- الملاحظة المؤكدة لا تمنح إذن إصلاح. القرار أحد repair / investigate / retain، وتُفصل جاهزيته عن ثقته.
- الإصلاح يحتاج مطلبًا مسندًا وملاحظة مخالفة ومراجعة وقبل/بعد وفحوص قبول. التحقيق يمكن أن ينتهي بإبقاء موثق دون patch.
- التحقق مربوط ببصمة المرشح؛ له pass / fail / blocked / inconclusive، ولا ينفذ الأمر دون `--execute`. لا يمثل ذلك عزلًا أمنيًا للعملية؛ شغّله على نسخة مرشح موثوقة.
- إعادة بناء dossier ليست قبولًا سلوكيًا. تغير المصدر أثناء الفحص يمنع النجاح.
- موجات العمل تحترم الاعتماد السببي وسببه، وتفصله عن تعارض الملفات. تقدير الجهد غير المقاس يظهر unknown.
- المعرفات المستمرة منفصلة عن أرقام العرض؛ اختلاف العبارة لا يغير هوية مجس محدد. الحالات غير القابلة للمطابقة تبقى مجهولة، والهويات المكررة تُعرض كالتباس.
- اختفاء claim يظهر unobserved، ولا يُسمّى resolved دون إثبات. إغلاق الإصلاح آليًا من سجل فحوص متكامل لم يُنفذ بعد.
- يستطيع المسار الدلالي طلب نطاقات مصدر ووثائق خارج ملخص المكونات. النطاقات مربوطة ببصمة، ومحدودة الميزانية ومنقحة للأسرار؛ يصرّح بالاستبعادات. الاستنتاجات لا ترتفع تلقائيًا إلى CONFIRMED.
- قرار المراجع يدخل عبر `decision-review`، ويتحقق من مراجع الأدلة ومن حداثة المصدر، ويحفظ الحدث قبل/بعد. مراجعة بشرية مُعلنة ليست نتيجة نموذج آلي.
- تحديث السجل يعيد إنشاء البطاقات والصفحات ويزيل البطاقات الملغاة. تظهر البطاقات في HTML وروابطها قابلة للتنقل.
- قياس الدقة لا يحتسب الادعاءات غير المحكّمة صحيحة؛ مطابقة النصوص تبقى قياس اكتشاف أنماط فقط.

## إدخال مراجعة وتحقيق

```bash
.venv/bin/python -m eaos decision-review --out /workspace/project-review \
  --review /absolute/review.json
.venv/bin/python -m eaos acceptance /absolute/candidate \
  --check /absolute/check.json --execute --out /workspace/check-result.json
```

قرار إبقاء نموذجي (يستبدل المعرف بمعرف موجود):

```json
{"claim_id":"CLM-001","outcome":"retain","reviewed_by":"owner","reason":"تمت مراجعة سياقي القاعدتين؛ اختلافهما مقصود ومطلوب."}
```

قرار إصلاح يحتوي assessment بالحقول `reviewed_by`, `violated_invariant`, `requirement_refs`, `evidence_refs`, `before`, `after`, `proposed_change`؛ كل مرجع يجب أن يوجد في حقائق الفحص أو نطاقات المصدر المسجلة. ويمكن إرفاق `prerequisites` بمراجع claim_id وسبب الاعتماد.

فحص الأمر يحتوي `id`, `kind: command`, `invariant`, `expected`, `expected_exit`, `cwd: .`, `argv` كمصفوفة، و`source_revision` من `eaos.acceptance.fingerprint(candidate)`. تُراجع دلالة الأمر؛ نجاح exit code وحده لا يثبت أن المراجع اختار اختبارًا كافيًا. يدعم عقد الفحص أيضًا `kind: human` مع rubric، ويبقى محجوبًا عن النجاح الآلي.
