# EAOS داخل المساعد الذكي (MCP)

> الوضع: قرار المالك (2026-09-28): EAOS يُضاف إلى Claude Code أو Codex خادمَ MCP، والمساعد يدير العمل كله بأدواته.
> المهام في `docs/north-star.json`: NS9.T7 إلى NS9.T9، ثم NS9.T6 (الدليل والتجربة الكاملة). المؤشران X8 وX9.

## الفكرة

المستخدم يكتب لمساعده بكلامه: «افحص مشروعي وأصلح أهم المشاكل». المساعد يشغّل أدوات EAOS، ويقرأ الكود بنفسه، ويكتب
الإصلاحات، وEAOS يتحقق من كل إصلاح ويسلّمه فرعًا. يرجع المساعد إلى المستخدم مرتين فقط: موافقة واحدة قبل تشغيل البرنامج
وتعديل الكود، وقرار في النهاية (يعتمد الإصلاحات أو يتراجع عنها).

| المساعد (Claude أو Codex) | EAOS |
| --- | --- |
| يفهم الطلب ويقرر الخطوات | أدلة دقيقة: المشاكل وأماكنها، والبنية، والخطة |
| يقرأ الكود ويكتب الإصلاح | نسخة معزولة من المشروع، وقاعدة بيانات محلية |
| يقترح طريقة تشغيل البرنامج حين لا يكفي الاكتشاف | يرفض ما ليس آمنًا، ويشغّل، ويرجع النتيجة كما هي |
| يشرح للمستخدم بكلام بسيط | البوابات: المشكلة اختفت، لا شيء انكسر، الشاشات كما هي، لا ميزة حُذفت؛ ثم فرع مستقل |

EAOS لا يستدعي نموذجًا بنفسه في هذا الطريق: عقل العمل هو المساعد الذي يستخدمه المستخدم، بكل ما يرى من المشروع.
قواعد الأمان في EAOS لا في التعليمات: لا عنوان خارج هذا الجهاز، لا أمر خارج مدير الحزم وnode، لا لمس لفرع المستخدم.

## الأدوات

كل أداة تأخذ `project` (مجلد المشروع؛ الافتراضي المجلد الذي فُتح فيه المساعد). العمل الطويل مهمة (job) تُتابَع بـ`wait`.

| المجموعة | الأداة | ما تفعله |
| --- | --- | --- |
| الحال | `status` | أين وصل المشروع، والأداة التالية، والتقدم، والتسليم (`handover`): ما عمله آخر مساعد وكيف يُكمَل |
| | `branches` و`choose_branch` | فروع الشخص (بلا فروع البوتات وفروع EAOS) بتاريخ آخر تغيير والتقدّم على الفرع الرئيسي والتوصية؛ واختيار الفرع الذي يتبعه كل شيء بعد ذلك |
| | `note` | ملاحظة لمن يكمل العمل (المساعد نفسه بعد انقطاع، أو غيره): لماذا قرر ما قرر، وما كان سيفعله |
| التشخيص | `audit` | الفحص الكامل (26 مرحلة) مهمةً؛ يُستأنف إن انقطع، ولا يعاد لنفس النسخة |
| | `wait` | ينتظر مهمة حتى دقيقة، ويرجع تقدمها أو نتيجتها |
| | `overview` | صحة المشروع: الأعداد، وأهم المشاكل، والخطة، وما لم يكتمل |
| | `findings` | المشاكل بتصفية (الخطورة، النوع، الملف، نص) |
| | `finding` | مشكلة واحدة كاملة: الدليل، ومقتطف الكود، والتحقق، والإصلاح المقترح |
| | `structure` | البنية: الطبقات، والمخالفات، والحلقات، والبنية المستهدفة |
| | `plan` و`card` | خطة الإصلاح بمراحلها، وبطاقة واحدة كاملة |
| | `report_file` | أي ملف من التقرير الفني |
| | `open_report` | يفتح تقرير البشر (REPORT.html) في المتصفح |
| التشغيل | `run_setup` | بعد موافقة المستخدم: يكتشف طريقة التشغيل ويجرّبها في نسخة معزولة |
| | `run_try` | يجرّب اقتراح المساعد (بيئة، أوامر، سكربت بيانات) بعد فحص الأمان |
| | `safety_net` | يصوّر الشاشات ويقيس السرعة قبل أي إصلاح |
| الإصلاح | `fix_start` | يفتح دفعة في نسخة معزولة، ويطبّق الإصلاحات الآلية (codemods)، ويرجع ما يحتاج المساعد |
| | `fix_read` | يقرأ ملفًا في النسخة المعزولة كما هو الآن |
| | `fix_edit` | يطبّق تعديل المساعد لبطاقة، ويفحصه فورًا؛ الفاشل يُرجع بسببه |
| | `fix_skip` | يترك بطاقة بسبب |
| | `fix_finish` | فحوص المشروع وقفل السلوك على الدفعة كلها، ثم فرع `eaos/wave-N` في المشروع |
| | `accept` و`undo` | يدمج الفرع (بعد موافقة المستخدم) ثم يحذفه ويحدّث التقرير والتقدم في النداء نفسه، أو يحذفه بلا دمج |

| البناء من خطة | `blueprint_start` و`blueprint_spec` و`blueprint_design` | يقرأ أي خطة، ويفحص المواصفات، ويرسم البنية والتقنيات وخطة البناء ([`docs/BUILD-FROM-PLAN.md`](BUILD-FROM-PLAN.md)) |
| | `build_start` و`build_read` و`build_edit` و`build_skip` و`build_finish` | يبني مرحلة مرحلة، وكل بطاقة خلف البوابات، وكل مرحلة فرع `eaos/build-N` |

وأوامر جاهزة (prompts) تظهر في Claude Code: `/mcp__eaos__audit` و`/mcp__eaos__fix` و`/mcp__eaos__build` و`/mcp__eaos__status`.

## المخرجات: مجلد واحد لكل مشروع

كل ما يصنعه EAOS للمستخدم في مجلد واحد ظاهر: `~/EAOS/<اسم المشروع>/`، لا في مشروعه ولا مبعثرًا:

| الجزء | ما فيه |
| --- | --- |
| `REPORT.html` | التقارير الأربعة للبشر في صفحة واحدة: ملخص المشروع، والفجوات والمخاطر، وخريطة البنية، والخطة والتقدم. يُعاد بناؤه بعد كل دفعة |
| `technical/` | التقرير الفني الكامل كما هو، لمساعد الذكاء الاصطناعي وللمطوّرين |
| `fixes/wave-N/` | كل دفعة: `SUMMARY.md` بكلام بسيط، وملفات `.patch`، و`wave.json` |
| `logs/` | السجلات التقنية |
| `HANDOVER.md` | أين العمل الآن، وما عمله آخر مساعد، وكيف يكمله غيره؛ يُكتب بعد كل خطوة |
| `README.md` | ما في كل جزء |

ما ليس مخرجًا (الحالة، والنسخ المعزولة، ومتابعة المهام) يبقى في `~/.eaos/` الخفي. الأداة `open_report` تفتح التقرير في المتصفح.

## التثبيت

سطر `install.sh` نفسه، ثم يسجّل EAOS في Claude Code (`claude mcp add --scope user`) وفي Codex (`~/.codex/config.toml`)
تلقائيًا. لا ملف يكتبه المستخدم. الأوامر (`eaos start` وغيرها) تبقى طريقًا ثانيًا.

## الاستمرارية: تقدم صادق، ودمج يغلق الحلقة، وتسليم بين المساعدين

- **السجل (`eaos/ledger.py`):** لكل بطاقة مفتاح ثابت (نوعها وملفاتها وكلماتها بلا أرقام)، لأن الفحص يرقّم بطاقاته من
  جديد كل مرة. كل commit من EAOS يحمل `EAOS-Card: <المفتاح>`، فما دُمج يُقرأ من فرع الشخص نفسه، أيًّا كان من دمجه وكيف.
  حالة البطاقة: مفتوحة، في الدفعة، على فرع ينتظر القرار، منجزة (مدموجة)، زالت في فحص لاحق، تحتاج قرارًا. التقرير
  يقرأ التقدم من السجل وحده، ولا يعدّ المنتظر على فرع منجزًا.
- **الدمج (`guided.merge` و`guided.reconcile`):** `accept` يدمج (سريعًا، وإلا دمجًا نظيفًا؛ التعارض يُلغى فلا يتغير
  شيء)، ثم يحذف الفرع ويعيد بناء التقرير. و`status` يطابق الحالة مع git في كل نداء: فرع دُمج يدويًا يُسجّل ويُحذف،
  وفرع حُذف بلا دمج يُعدّ تراجعًا. بعد دمج إصلاحات EAOS وحدها لا حاجة لفحص جديد ولا لتشغيل جديد.
- **التسليم (`eaos/handover.py`):** خادم MCP يكتب كل نداء في `journal.jsonl` (متى، وأي مساعد، وأي أداة، وأي بطاقة، وما
  النتيجة)، و`note` يضيف السبب، و`HANDOVER.md` يُعاد كتابته بعد كل خطوة. المساعد التالي يستدعي `status` أولًا فيجد
  `handover`: العمل المفتوح وما بقي منه، وما أجاب عنه الشخص، وآخر الخطوات والملاحظات، وكيف يكمل. التجربة:
  `tools/handover_trial.py` (Codex يُقطع وسط دفعة، وClaude Code يكمل، ثم الدمج).
- **الفرع (`eaos/branches.py`):** حين يكون للمشروع أكثر من فرع للشخص بكود مختلف، يسأل `status` أولًا أي فرع (بتوصية:
  الأكثر تقدّمًا على الفرع الرئيسي)، ولا يبدأ الفحص قبل الجواب؛ وإلا فالفرع المفتوح بلا سؤال. الفحص والتشغيل والنسخ
  المعزولة تُقرأ من نسخة EAOS للفرع (`guided.source`) إن لم يكن هو المفتوح، فلا يتبدّل فرع الشخص. الدمج في الفرع المختار:
  في مجلد الشخص إن كان مفتوحًا، وإلا في نسخة EAOS ثم يتحرك الفرع إن لم يحرّكه أحد. لكل فرع فحصه وسجله ودفعاته وتقريره:
  أول فرع في أعلى مجلد المخرجات، وغيره في `branches/<الاسم>/`، والتقرير يسمّي فرعه ويربط بتقارير الفروع الأخرى.
- **بداية الجلسة (`eaos handover --hook`):** `eaos assistant install` يضيف SessionStart hook في `~/.claude/settings.json` و`~/.codex/hooks.json`
  (Codex يطلب من الشخص الموافقة عليه مرة). حين يكون لـEAOS عمل مفتوح في المجلد (أو في المستودع الذي هو داخله)، تبدأ الجلسة
  وهي تعرف: آخر خطوة ومن عملها، والدفعة وما حُفظ منها وما بقي، والبطاقة التي كان عليها وما قرأ لها (`handover.in_progress`)؛
  فكلمة «كمّل» وحدها تكفي. والشخص يرى نفس الشيء بـ`eaos resume` وفي قسم «سجل العمل» في التقرير.
- **التقرير مضمون (`guided.publish`):** لا يبلع خطأ: الجزء الذي لم يُبنَ يُكتب اسمه وسببه أعلى الصفحة وفي `.report.json` وفي `logs/`،
  وكل صفحة مختومة بنسخة EAOS والـcommit ووقت البناء (`eaos/build_info.py`)، و`status` يعيد بناء صفحة بنتها نسخة أقدم فورًا.
