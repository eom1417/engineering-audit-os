# خطة التحول التنفيذية إلى تقرير موثوق وخطة تطوير قابلة للتحقق

> مولَّد من docs/transformation.json؛ لا تحرره يدويًا.

**الحالة:** خطة تنفيذ؛ اكتمال الخطة ليس اكتمال المنتج. حالات done موروثة وليست اختبارًا أُعيد في إعداد هذه الوثيقة.

ابدأ من [EXECUTION-START.md](EXECUTION-START.md). الاعتماديات الملزمة على مستوى المهمة؛ المرحلة حزمة تسليم وليست منعًا لبدء مهمة مستقلة.

## قواعد التنفيذ

1. ابدأ من docs/EXECUTION-START.md ثم نفذ python tools/render_transformation.py --next. الملف JSON هو مصدر حالة المهام الوحيد.
2. اقرأ بطاقة docs/tasks/<ID>.md ومراجعها. فرّق بين existing (موجود الآن) وplanned (ينتجه prerequisite)؛ لا تفترض وجود اختبار لم يُكتب.
3. نفذ أول مهمة todo اكتملت جميع task.depends_on الخاصة بها. داخل المهمة نفذ الخطوات بالترتيب، وابدأ بحالة فشل تثبت المشكلة ثم نفذ الإصلاح.
4. قبول المهمة يتطلب أمر التحقق + تحقق شروط acceptance_cases + سجل evidence. خروج صفر لا يثبت جودة الحكم الهندسي أو المراجعة البشرية.
5. سجل الاختبارات المنفذة والنتائج والنسخة والقيود في docs/task-results/<ID>.json، ولا تسجل اختبارًا محجوبًا كنجاح.
6. عند غياب مزود أو شبكة أو مراجع مستقل، سجل blocked والسبب والخطوة التالية، وتابع مهمة مستقلة. لا تستبدل التقييم الحي بمزود scripted وتدّعي النجاح.
7. لا تحذف قدرة قديمة قبل اختبار التكافؤ والتوافق وتوثيق أثر الانتقال. لا تحسن رقمًا بإخفاء ملفات أو إسكات قاعدة بلا سبب هندسي.
8. حدّث حالة المهمة في JSON وشغّل renderer ثم بوابة الاختبارات. لا تعدّل الوثائق المولدة مباشرة، ولا تعِد تنفيذ done دون دليل تراجع.
9. أنجز المهام محليًا؛ لا يتطلب التسليم نشرًا أو إرسال بيانات خارجية أو تعديل مستودعات المنابع. حفظ commit منفصل مستحسن عند اعتماد تغير المهمة وليس دليل قبول بحد ذاته.

## بوابة التكامل

```bash
python -m unittest discover -s tests -q && python tools/validate.py && python -m eaos policy check . --out /workspace/eaos-plan-handoff/policy && python tools/render_transformation.py --check
```

مشكلة البيئة أو غياب مزود/محرك ليست نجاحًا. دليل البشرية والنموذج الحي مطلوب في مهامه المحددة ولا تستبدله الاختبارات الآلية.
